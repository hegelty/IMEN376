# AI 수요예측 파트 발표자료용 최종 서술본 — Corrected Version

## Cass 수요예측 모델 구축과 발효탱크 운영 적용

---

## 1. 분석 목적

Cass 맥주는 계절성과 이벤트 영향을 크게 받는 제품이다. 여름철 폭염, 열대야, 야구 경기, 월드컵 같은 스포츠 이벤트, 가격 인상 전 선구매 수요는 월별 수요 변동을 크게 만들 수 있다.

반면 맥주 생산에는 발효 리드타임이 존재한다. 수요가 이미 발생한 뒤에 생산량을 늘리려고 하면, 발효탱크와 숙성 공정 때문에 즉시 대응하기 어렵다. 따라서 Cass 생산계획에서 중요한 것은 수요 발생 후 대응이 아니라, 수요가 발생하기 전에 미리 생산량과 발효탱크 배분을 결정하는 것이다.

본 프로젝트의 AI 예측 파트는 다음 질문에 답하기 위해 설계되었다.

> “공개 데이터만으로 Cass 관련 맥주 수요를 사전에 예측하는 MVP 시스템을 만들 수 있는가?”

다만 시작부터 중요한 제약이 있다. 실제 OB 내부의 Cass Fresh, Cass Light, Cass 0.0 월별 판매량 또는 출고량은 공개되어 있지 않다. 따라서 본 프로젝트는 실제 운영 모델을 완성했다기보다, 공개 데이터 기반으로 AI 수요예측 시스템의 가능성을 검증하는 Phase 0 MVP로 해석해야 한다.

---

## 2. 수요 데이터 확보의 현실적 한계

AI 수요예측 모델에서 가장 중요한 것은 target, 즉 실제로 예측해야 하는 수요 데이터이다. 이상적으로는 다음과 같은 데이터가 필요하다.

| 이상적인 target | 설명 |
|---|---|
| Cass Fresh 월별 출고량 | 실제 SKU 단위 생산·판매 계획에 직접 사용 가능 |
| Cass Light 월별 출고량 | SKU별 발효탱크 배분 가능 |
| Cass 0.0 월별 판매량 | 비알콜 제품 성장성 반영 가능 |
| 지역/채널별 POS 판매량 | 편의점, 마트, 유흥 채널별 수요 차이 반영 가능 |
| 도매상 주문 데이터 | bullwhip effect 및 선주문 수요 분석 가능 |

하지만 이러한 데이터는 기업 내부 ERP, SAP, POS, 도매상 주문 시스템에 존재하는 데이터이며 공개되어 있지 않다. 따라서 본 프로젝트에서는 실제 Cass SKU 수요를 직접 target으로 사용할 수 없었다.

이 한계 때문에, 본 분석에서는 공개자료에서 확보 가능한 국내 알코올 맥주 시장 규모를 기반으로 월별 수요 proxy를 구성했다. 즉, 모델이 예측하는 것은 “실제 Cass 내부 판매량”이 아니라 “공개자료 기반 국내 맥주 수요 proxy”이다.

이 차이는 매우 중요하다.

> 본 프로젝트의 모델 성능은 실제 Cass SKU 수요에 대한 검증 성능이 아니라, 공개자료 기반 proxy target에 대한 진단적 성능이다.

## 3. Target을 임의로 만들면 안 되는 이유

AI 모델을 평가하려면 target은 모델이 맞혀야 하는 외부 현실이어야 한다. 만약 연구자가 target을 임의로 만들고, 다시 그 target을 예측하는 모델을 만든다면 성능 검증의 의미가 약해진다.

예를 들어 날씨, KBO 경기수, 공휴일 수를 이용해 월별 수요 target을 새로 만든 뒤, 다시 AI 모델에 날씨나 KBO 관련 변수를 넣어 그 target을 예측하게 하면 문제가 생긴다. 모델이 실제 시장 수요를 예측한 것이 아니라, 연구자가 만든 규칙을 다시 맞힌 것에 가까워질 수 있기 때문이다.

따라서 최종 발표에서는 다음 원칙을 적용한다.

| 원칙 | 내용 |
|---|---|
| target은 임의로 새로 만들지 않는다 | 모델 성능을 좋게 보이기 위해 수요 데이터를 재조정하지 않음 |
| 공개자료 기반 proxy임을 명시한다 | 실제 Cass 내부 수요가 아니라는 점을 숨기지 않음 |
| 성능은 diagnostic이라고 표현한다 | 실제 운영 성능으로 과장하지 않음 |
| SKU-level 성능은 주장하지 않는다 | Cass Fresh/Light 실제 수요 검증이 아니기 때문 |
| AI 모델의 역할은 MVP 검증으로 제한한다 | 내부 데이터 확보 시 확장 가능한 구조 제안 |

즉, 본 프로젝트에서는 수요 target을 “AI가 잘 맞히도록” 새로 만들지 않는다. 대신 공개자료 기반 수요 proxy를 그대로 사용하고, 그 한계를 명확히 인정한다.

## 4. 공개자료 기반 수요 proxy 구성

실제 Cass 월별 수요가 없기 때문에, 본 프로젝트에서는 공개자료를 바탕으로 세 단계의 수요 구조를 구성했다.

### 4.1 Layer A: 국내 알코올 맥주 전체 수요

첫 번째 layer는 국내 알코올 맥주 전체 시장 수요이다. 이는 국세통계연보 등 공개자료에서 확인 가능한 국내 맥주 출고량을 기반으로 한다.

이 값은 Cass만의 수요는 아니지만, 국내 맥주 시장 전체의 계절성과 규모를 파악하는 기준점으로 사용할 수 있다.

### 4.2 Layer B: Cass Fresh / Cass Light 점유율

두 번째 layer는 Cass 브랜드 점유율이다. 언론 보도 등 공개자료에서 확인 가능한 Cass Fresh와 Cass Light의 시장점유율을 연도별 anchor로 사용한다.

이를 통해 전체 맥주 시장 수요를 Cass 브랜드 수요로 대략 분해할 수 있다.

예를 들어 전체 국내 맥주 수요가 증가하고 Cass 점유율이 일정하다면, Cass 수요도 유사하게 증가한다고 볼 수 있다.

### 4.3 Layer C: Cass 0.0 비알콜 시나리오

세 번째 layer는 Cass 0.0과 같은 비알콜 맥주 시장이다. 비알콜 시장은 아직 전체 맥주 시장에 비해 작지만 성장성이 높기 때문에, base / low / high 시나리오로 구분하여 반영한다.

정리하면, 본 프로젝트의 수요 구조는 다음과 같다.

| Layer | 의미 | 역할 |
|---|---|---|
| Layer A | 국내 알코올 맥주 전체 수요 | 모델의 기본 예측 target proxy |
| Layer B | Cass Fresh / Light 점유율 | 전체 시장 수요를 Cass 브랜드로 분해 |
| Layer C | Cass 0.0 비알콜 시나리오 | 성장 제품군 시나리오 반영 |

이 방식은 완벽한 실측 수요는 아니지만, 내부 데이터가 없는 상황에서 공개자료만으로 만들 수 있는 가장 방어 가능한 수요 proxy이다.

## 5. 외생변수 수집

맥주 수요는 과거 수요뿐 아니라 날씨, 스포츠, 공휴일, 가격 변화, 뉴스 이벤트의 영향을 받을 수 있다. 따라서 본 프로젝트에서는 수요를 설명할 수 있는 외생변수를 함께 수집했다.

### 5.1 날씨 변수

더운 날씨는 맥주 수요 증가와 직관적으로 연결된다. 따라서 다음 변수를 수집했다.

- 월평균기온
- 폭염일수
- 열대야일수
- 강수량
- 비 오는 날 수

### 5.2 스포츠 및 이벤트 변수

맥주는 스포츠 관람과 모임 수요와 연결된다. 따라서 다음 변수를 반영했다.

- KBO 정규시즌 경기수
- KBO 포스트시즌 경기수
- 월드컵 등 주요 스포츠 이벤트
- 지역 축제 수
- 맥주 축제 관련 이벤트 수

### 5.3 달력 변수

공휴일과 연휴는 외식, 여가, 모임 수요를 증가시킬 수 있다.

- 공휴일 수
- 주말 수
- 평일 공휴일 수
- 긴 연휴 여부

### 5.4 가격 및 경제 변수

가격 변화는 선구매 또는 대체재 선택에 영향을 줄 수 있다.

- 수입맥주 단가 변화율
- 소비자물가지수 상승률
- OB 가격 인상 이벤트 더미
- 가격 인상 이후 경과 개월 수

### 5.5 뉴스 및 관심도 변수

시장 분위기와 이벤트성 수요를 반영하기 위해 뉴스 기반 변수도 사용했다.

- 맥주 관련 뉴스 수
- Cass/OB 관련 뉴스 수
- 비알콜 맥주 뉴스 수
- 날씨와 수요 관련 뉴스 수
- 축제/맥주 행사 뉴스 수

## 6. Google Trends 처리 원칙

Google Trends는 소비자 관심도를 나타내는 좋은 수요 선행 지표가 될 수 있다. 예를 들어 “카스”, “맥주”, “무알콜 맥주” 검색량 증가는 향후 수요 증가의 신호일 수 있다.

하지만 Google Trends는 target 생성과 모델 feature 사용을 구분해야 한다.

### 6.1 Target 생성에는 사용하지 않는다

Google Trends를 이용해 수요 proxy를 만들고, 다시 Google Trends로 그 proxy를 예측하면 순환논리 문제가 생긴다.

```
Google Trends → 수요 proxy 구성
Google Trends → 모델 feature
```

이 경우 모델이 실제 수요를 예측한 것인지, 아니면 target 생성에 사용된 정보를 다시 읽은 것인지 구분하기 어렵다. 따라서 최종 발표에서는 Google Trends를 target 생성 근거로 사용하지 않는다.

### 6.2 예측 feature로는 조건부 사용 가능하다

실제 운영 예측에서는 Google Trends를 사용할 수 있다. 단, 당월 검색량으로 당월 수요를 예측하면 시점 문제가 생길 수 있으므로, 전달 검색량을 다음 달 수요 예측에 사용하는 방식이 더 방어 가능하다.

예를 들어 다음과 같은 구조이다.

```
5월 Google Trends → 6월 수요 예측
6월 Google Trends → 7월 수요 예측
```

본 프로젝트에서도 전달 Google Trends를 별도 실험으로 테스트했다. 그러나 현재 공개 proxy target에서는 성능 개선이 크지 않았다. 따라서 Google Trends는 최종 성능의 핵심 근거로 사용하지 않고, 실제 POS/출고 데이터가 확보되었을 때 재평가할 수 있는 demand-sensing 후보 변수로 정리한다.

## 7. 모델 후보

본 프로젝트에서는 하나의 모델만 사용하지 않고 여러 예측 모델을 비교했다. 그 이유는 AI 모델의 성능을 판단하려면 반드시 단순 기준선과 비교해야 하기 때문이다.

비교한 모델은 다음과 같다.

| 모델 | 설명 | 역할 |
|---|---|---|
| Seasonal Naive | 전년 동월 수요를 그대로 예측 | 필수 기준선 |
| Chronos-2 | Amazon의 시계열 foundation model | 핵심 AI 모델 후보 |
| Ridge | 정규화 선형회귀 | 안정적인 ML 기준선 |
| Lasso | 변수 선택 효과가 있는 선형회귀 | sparse model 후보 |
| ElasticNet | Ridge와 Lasso 혼합 | 선형 모델 보완 |
| RandomForest | 여러 decision tree 평균 | 비선형 모델 후보 |
| ExtraTrees | 무작위성이 큰 tree ensemble | robust tree 후보 |
| GradientBoosting | 순차적으로 오차를 줄이는 tree model | boosting 후보 |
| KNN | 과거 유사 월 기반 예측 | 유사 패턴 기반 후보 |
| SVR | kernel 기반 회귀 | 비선형 회귀 후보 |
| MLP | 신경망 회귀 | neural network 후보 |

평가는 2024년 1월부터 2025년 12월까지 24개월을 대상으로 수행했다. 각 월을 예측할 때는 그 월 이전 데이터만 학습에 사용했다. 즉, 미래 데이터를 미리 보고 학습하지 않도록 rolling backtest 방식으로 평가했다.

## 8. Chronos-2를 핵심 AI 모델로 사용한 이유

Chronos-2는 시계열 예측을 위해 사전학습된 foundation model이다. 일반적인 회귀 모델은 현재 데이터셋 안에서만 패턴을 학습하지만, Chronos-2는 다양한 시계열 패턴을 사전학습했기 때문에 작은 데이터셋에서도 zero-shot 방식으로 적용할 수 있다.

본 프로젝트에서 Chronos-2를 핵심 AI 모델 후보로 사용한 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 시계열 전용 모델 | 월별 수요 예측에 적합 |
| zero-shot 적용 가능 | 72개월의 작은 데이터에서도 적용 가능 |
| 분위수 예측 가능 | 중앙값뿐 아니라 상한/하한 예측 가능 |
| 운영 의사결정 연결성 | Q90 상한을 안전재고와 발효탱크 계획에 활용 가능 |
| 이벤트 리스크 대응 | 수요 급등 가능성을 구간 예측으로 표현 가능 |

Cass 생산에서는 평균 예측값만 중요한 것이 아니다. 수요가 예상보다 높게 나올 경우 품절과 공급 부족이 발생할 수 있기 때문에, 상한 예측값이 중요하다. Chronos-2는 이러한 예측구간을 제공한다는 점에서 운영적으로 의미가 있다.

## 9. 모델 결과 해석

공개자료 기반 수요 proxy에 대해 여러 모델을 비교한 결과, Seasonal Naive가 매우 강한 기준선으로 나타났다. 이는 놀라운 결과가 아니다. 현재 target은 실제 월별 Cass 판매량이 아니라 연간 공개자료를 월별로 배분한 proxy이기 때문에, 전년 동월 패턴이 강하게 반복될 수밖에 없다.

따라서 결과를 해석할 때 중요한 것은 “AI가 baseline을 압도했는가”가 아니라, “공개 proxy 데이터 조건에서 AI 모델이 어느 정도까지 작동하는가”이다.

Chronos-2는 일부 rolling backtest 및 이벤트 월 분석에서 Seasonal Naive와 유사하거나 근소하게 개선된 성능을 보였다. 특히 Chronos-2의 장점은 단순 점예측보다 예측구간을 제공한다는 점이다. 이는 발효탱크 운영에서 수요 상한을 고려한 보수적 계획에 활용될 수 있다.

결과를 정리하면 다음과 같다.

| 관찰 결과 | 해석 |
|---|---|
| Seasonal Naive가 매우 강함 | target이 월별 proxy라 전년 동월 패턴이 강함 |
| Chronos-2는 baseline과 유사한 수준 | 공개 데이터만으로도 foundation model 적용 가능성 확인 |
| 이벤트 월에서 AI 활용 가치 존재 | 폭염·스포츠 이벤트 등 불확실성 관리에 의미 |
| ML 모델 다수는 불안정 | 72개월 월별 데이터는 복잡한 모델 학습에 작음 |
| 예측구간이 운영적으로 중요 | 발효탱크 배분에는 평균보다 상한 리스크가 중요 |

---

## 10. 최종 모델 선택

최종 AI 예측 모델은 Chronos-2로 설정한다. 다만 이 선택은 “Chronos-2가 모든 지표에서 압도적으로 우수하다”는 의미가 아니다. 현재 데이터는 공개자료 기반 proxy이므로, Seasonal Naive가 매우 강한 baseline이다.

그럼에도 Chronos-2를 최종 AI 모델로 선택하는 이유는 다음과 같다.

첫째, Chronos-2는 공개 월별 proxy 데이터에서도 정상적으로 작동하며, baseline과 비교 가능한 수준의 예측 성능을 보였다.

둘째, Chronos-2는 단순 점예측뿐 아니라 분위수 예측을 제공한다. 이는 발효탱크 운영에서 매우 중요하다.

셋째, 폭염·스포츠 이벤트·가격 인상 등 불확실성이 큰 월에는 중앙 예측값보다 상한 예측값을 참고하는 것이 운영적으로 더 안전하다.

넷째, 실제 Cass SKU별 수요 데이터가 확보되면 Chronos-2 구조를 그대로 Phase 1 운영 모델로 확장할 수 있다.

따라서 최종 운영 구조는 다음과 같다.

```
Chronos-2 월별 수요예측
  ↓
Seasonal Naive baseline과 비교
  ↓
예측값이 유사하면 Chronos-2 중앙값을 기본 예측으로 사용
  ↓
이벤트 월 또는 예측구간이 넓은 월은 Chronos-2 Q90 상한 확인
  ↓
발효탱크 배분, 안전재고, 계획팀 검토로 연결
```

즉, 최종 모델은 다음 문장으로 요약할 수 있다.

> “Chronos-2를 AI forecast model로 사용하되, Seasonal Naive를 sanity-check baseline으로 병행하고, 이벤트 월에는 Chronos-2 Q90 상한을 risk overlay로 활용한다.”

## 11. 발효탱크 운영과의 연결

AI 수요예측의 최종 목적은 예측 정확도를 보고서에 제시하는 것이 아니라, 실제 운영 의사결정에 연결하는 것이다.

Cass 생산에서는 발효탱크가 병목 자원이다. 수요가 급증했을 때 이미 늦게 대응하면 발효 리드타임 때문에 공급을 즉시 늘릴 수 없다. 따라서 수요예측 모델은 다음과 같이 사용될 수 있다.

| 예측 상황 | 운영 대응 |
|---|---|
| 중앙 예측값이 전년 동월과 유사 | 기존 발효 계획 유지 |
| 중앙 예측값이 전년 동월보다 높음 | 생산계획 상향 검토 |
| Q90 상한이 크게 높음 | 안전재고 추가 또는 발효탱크 선배분 검토 |
| 여름 성수기·KBO 집중 월 | 계획팀장 검토 및 보수적 생산계획 |
| 예측구간이 넓음 | 불확실성 alert 발생 |

예를 들어 7월 성수기 수요에 대응하려면, 실제 7월 주문이 들어온 뒤 대응해서는 늦다. 발효 리드타임을 고려하면 6월 중순 이전에는 발효량과 탱크 배분을 결정해야 한다. 따라서 AI 예측은 사후 분석이 아니라 사전 생산계획을 위한 의사결정 도구이다.

## 12. 본 분석의 한계

본 분석은 공개 데이터 기반 MVP이므로 명확한 한계가 있다.

첫째, 실제 OB 내부 월별 Cass 판매량이 없다. 따라서 모델이 예측한 target은 실제 Cass SKU별 수요가 아니라 공개자료 기반 국내 맥주 수요 proxy이다.

둘째, 월별 데이터가 72개월뿐이다. 복잡한 AI 모델이나 딥러닝 모델을 안정적으로 검증하기에는 데이터 수가 작다.

셋째, Cass Fresh, Cass Light, Cass 0.0의 실제 SKU 단위 성능은 검증할 수 없다. 브랜드 점유율로 분해할 수는 있지만, 그것은 실측 SKU 수요가 아니다.

넷째, Google Trends의 효과도 현재 proxy target에서는 제한적으로만 확인된다. 실제 POS나 출고량 데이터가 있으면 검색량의 선행 효과를 더 정확히 평가할 수 있다.

한계를 표로 정리하면 다음과 같다.

| 한계 | 설명 |
|---|---|
| 실제 내부 수요 부재 | ERP/SAP/POS 기반 Cass 월별 수요가 없음 |
| target은 공개자료 기반 proxy | 실제 운영 target이 아니라 진단용 target |
| SKU 검증 불가 | Cass Fresh/Light 월별 실측치 없음 |
| 표본 수 작음 | 72개월로 복잡한 모델 검증에 제한 |
| Google Trends 효과 제한 | 실제 판매량 target 확보 시 재평가 필요 |

## 13. 결론

본 프로젝트는 공개 데이터만을 이용해 Cass 수요예측 모델을 구축하고, 이를 발효탱크 사전 배분 의사결정과 연결하는 AI 예측 시스템을 설계했다.

가장 중요한 점은 실제 Cass 내부 수요 데이터가 없다는 한계를 숨기지 않았다는 것이다. 본 분석에서는 예측해야 할 수요를 임의로 새로 만들지 않고, 공개자료 기반 수요 proxy를 사용했다. 이 target은 실제 SKU 수요가 아니므로 모델 성능은 운영 확정 성능이 아니라 diagnostic 성능으로 해석해야 한다.

그럼에도 본 분석은 의미가 있다. 공개 데이터만으로도 수요예측 pipeline을 만들 수 있었고, Chronos-2 같은 시계열 foundation model을 적용해 baseline과 비교 가능한 예측 결과를 얻었다. 또한 단순 점예측을 넘어 Q90 상한을 활용한 발효탱크 risk overlay 구조를 제안했다.

최종 제안은 다음과 같다.

1. 현재 단계에서는 공개자료 기반 수요 proxy를 이용한 Phase 0 MVP로 정의한다.
2. Chronos-2를 AI forecast model로 사용한다.
3. Seasonal Naive를 강한 sanity-check baseline으로 병행한다.
4. 이벤트 월에는 Chronos-2 Q90 상한을 활용해 안전재고와 발효탱크 배분을 검토한다.
5. 실제 OB 내부 Cass SKU별 월별 수요가 확보되면, 동일 pipeline을 Phase 1 운영 모델로 확장한다.

따라서 본 AI 예측 파트의 결론은 “공개 데이터만으로 완전한 운영 모델을 만들었다”가 아니라, “공개 데이터만으로도 수요예측 MVP와 운영 의사결정 구조를 설계할 수 있으며, 내부 데이터 확보 시 실제 운영 모델로 확장 가능하다”이다.
